# Item 6 run, 10 September 2026 — one submission, sent back and corrected

Against uvicorn on the dev database (migrations through 016), the console in
Chrome, and the `Pixel_8` emulator. Everything below is what was seen.

## What the run was for

The item's whole claim, in one loop: a rule fires on arrival, a supervisor
sends the work back with a reason, the enumerator reads that reason on the
handset, corrects the answer, and the **same** submission returns to the queue
with the flag resolved. If any link is broken the loop is a set of screens.

## The rule

Made through the API as the programme manager, with a deliberate typo first:

```
POST /api/v1/quality/rules  {"name":"broken","definition":{"op":"call","fn":"no_such_function","args":[]}}
{"detail":{"reason":"invalid_expression","message":"unknown function: no_such_function"}}
```

Refused at the author, with the compiler's own message, which is the point:
stored, it would have become a `not_evaluated` row on every submission for as
long as it stayed enabled. The real rule is an IR expression and nothing else:

```json
{"op": "call", "fn": "contains",
 "args": [{"op": "ref", "path": "enumerator_name"}, {"op": "lit", "value": " "}]}
```

"The enumerator's name must be a full name." No second language, no second
evaluator — this is the expression the form engine already runs, held to the
same 116 conformance vectors.

## The handset, first pass

A cleared install, signed in as the team A enumerator, synced, forms
downloaded. A new Household Survey with `enumerator_name` = **Ravi** — one
word, so the rule will not hold.

Finalising was refused first: **"Cannot finalize: 1 answer(s) need attention"**,
and the screen moved to the blocker, the interview date, with "This answer is
required" under it. That is item 0's gate doing its job and it is worth noting
because it is the same shape as this item's refusals — say what is wrong and
where.

Date filled, consent answered, finalised, synced. On the server, in the push
transaction:

```
quality_flag | violation | Enumerator name must be a full name | warning | finalized
```

The rule ran on arrival, against the fold that push had just computed.

## The supervisor's queue

`/submissions?queue=true&flagged=true` — two checkboxes on the submission list,
labelled "Waiting for review" and "Flagged only". Not a screen of its own: two
lists of the same rows can disagree, and there is nothing a queue knows that
this list does not.

Signed in as **the supervisor**, which is the change A9 made: 008 gave
`submission.review` to Admin and Programme manager on the reading that review
is back-office work, and RCons's reviewers are supervisors. One row, the
flagged submission.

Opening it: **"1 rule flagged this"** over the rule's name and severity.

Choosing "Send back for correction" changed the field's label to **"What needs
correcting"** and added the sentence "Required. This is what the enumerator
reads on the handset before they open the form again — without it the visit is
repeated rather than corrected." **The button was disabled** until something was
typed. The server refuses either way; a screen that lets somebody find that out
by being refused has taught them nothing.

Recorded. The status badge became **correction required**, and the decision
appeared under it with the reason and who made it.

## Back on the handset

One sync. The row now reads:

> **Household Survey** · v1 · 2026-09-10 10:43 — **Sent back**
> *Please record the full name as on your ID card, not just the first name.*
> Sent back 2026-09-10 10:41

The reason is **on the row**, not behind the tap, and it carries the time the
**decision** was made rather than when this device heard about it.

### What the run found

Tapping it opened the form **read-only** — "Finalized" in the header, every
control disabled. Being shown what to correct and then prevented from
correcting it is worse than not being told: a dead end with an instruction on
it.

The cause is an ordering that reads as harmless. The view model fetches the
submission's summary, appends the `reopen` op, and then builds its state from
the summary fetched **before** the append — so the status in hand is the one
from before the function acted. Fixed, with `ReturnedWorkTest` as the
regression (break 219).

After the fix the same tap opens at **1 / 3** with `Ravi` in the field and
editable. Corrected to `Ravi Kumar`, paged on, finalised, synced.

## The server, afterwards

```
submission                    status = finalized
submission_state              {"consent":"no","interview_date":"2026-09-10",
                               "enumerator_name":"Ravi Kumar"}
quality_flag                  violation | Enumerator name must be a full name | resolved
submission_op   1 set enumerator_name · 2 set consent · 3 set interview_date
                4 finalize · 5 reopen · 6 unset enumerator_name
                7 set enumerator_name · 8 finalize
```

Four things in that, and they are the item:

- **One submission.** Same id, one op log, appended to. The export has no case
  column, so a correction returned as a second submission would have been two
  rows for one household with nothing in the file to group on — the failure the
  brief predicted, prevented by construction rather than by deduplication.
- **`finalized` again.** Defect 27's fix, in the field: before it, a submission
  that reached `correction_required` could never leave, and this one would have
  sat there with the corrected answers behind it, out of the queue and out of
  item 5's coverage, with nothing erroring.
- **The reopen is op 5, authored by the device.** The server cannot author it —
  `submission_op.device_id` is NOT NULL and `(device_id, counter)` is unique per
  device, so a counter allocated on the enumerator's handset collides with
  whatever it is about to push and the collision refuses the enumerator's own
  work. A6 proposed the server emit it; building it showed it cannot. The
  decision travels as a statement in the pull instead, and the device that
  holds the work writes the op.
- **The flag is resolved, not edited.** The rule's name and definition as
  evaluated are still on the row, so the decision made under it can still be
  read as it was made.

And the panel now says **"Every rule ran and none of them found anything."** —
which it will only say when every rule actually ran. A project with no rules
says so instead, and rules that could not be evaluated get their own block and
their own sentence.
