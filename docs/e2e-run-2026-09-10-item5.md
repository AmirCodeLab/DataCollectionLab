# Item 5 run, 10 September 2026 — two supervisors side by side, and a number nobody computed

Against uvicorn on the dev database (migrations through 015) and the `Pixel_8`
emulator. Everything below is what was seen.

## What the run was for

Two questions, and the second is the one that found something.

1. **Does a supervisor's dashboard stop at their team?** Not "does it look
   scoped" — does A plus B come to *less* than the project, on every figure.
2. **Does a figure this server did not compute travel with the time it was
   reported?** "3 waiting" and "3 waiting, as of 08:14" are different claims.

## The dev database could not answer the first question

Team A and Team B, and nothing else. Every row in the development database
belongs to one of them, so the two supervisors' figures add to the project's
*exactly* and a policy that showed a supervisor everything would have walked
through the check unnoticed. That is the fixture rule in
`docs/project-conventions.md` — a fixture whose rows all fall inside the scope
under test cannot see a widened scope — applied to the database a run is walked
on rather than to a test.

Team C was added to `scripts/seed_dev.py` with one enumerator. The case nobody
held, `S4|2|1`, was then assigned to them **through the console as the manager**,
which produced item 2's refusal on the way:

> The database refused this: the case, team or person is outside what your roles
> allow, or the person is not in the team that holds the case.

An unassigned case has no team, so it cannot go straight to a person in one.
Team C first, then the person. Both assignments succeeded and the sample screen
showed `S4|2|1 · Team C · Dev Enumerator C`.

## The three dashboards

Read from `/api/v1/monitoring/overview` under each person's own session, which
is the same query the screen makes.

| | cases | finished | submissions | not against a case | devices |
|---|---|---|---|---|---|
| Programme manager (this project) | 5 | 0 | 13 | 11 | 17 |
| Supervisor A (your team) | 3 | 0 | 11 | 10 | 16 |
| Supervisor B (your team) | 1 | 0 | 0 | 0 | 0 |

A plus B is strictly less than the project on cases, submissions, work with no
case, and devices. It is not less on *finished*, and the run does not claim it
is: nothing is finished anywhere, so 0 + 0 = 0 and the inequality has nothing to
bite on. The one figure the walk could not exercise is named rather than
rounded up.

Supervisor A's screen carries the sentence that makes its zeros readable —
"Everything on this page is your team. A zero here means none of yours, not none
anywhere." — and **no quality-flag card**, because the server sends
`flagsOutstanding: null` while no rule exists to raise one. A card reading 0
would be an empty table wearing a measurement's clothes (A7). Neither supervisor
can see Dev Enumerator C or their handset; the manager sees both.

## The device panel

Two handsets reported a backlog during the run. In the row, beside the number,
not in a tooltip:

```
Dev Enumerator     dev_1758cfaf   2026-09-10 08:16   2 waiting, as of 2026-09-10 08:16
Dev Enumerator C   dev_e7653dd4   2026-09-10 08:34   2 waiting, as of 2026-09-10 08:34
```

Every other device says **not reported yet**, which is the whole point: this
server does not know what is in an outbox, and `0` there would be a lie with a
column behind it.

## What the run found: a fresh handset could not register

Clearing the app to give Team C its own device turned up an HTTP 500 on the one
path that has no principal at all.

> Could not sync with http://10.0.2.2:8000 … (device registration refused:
> HTTP 500 — Internal Server Error)

Registration writes a device row with `user_id NULL`. Migration 015's *write*
policy admits that on purpose, and its *read* policy does not — an unbound
handset belongs to nobody and is visible organisation-wide only. The ORM returns
the server-side defaults, so the statement is an `INSERT ... RETURNING`, and
PostgreSQL applies the read policy to the returned row. It then refuses it
reporting the **write** policy's error, "new row violates row-level security
policy for table device", which points the next reader at the clause that was
fine.

015 had a paragraph warning a later reader not to tidy the asymmetry away, and
it listed "exactly three statements that must work before anybody has signed
in". There were four. The insert now goes through `dcp_device_register`, a
fourth definer function that writes `user_id NULL` and nothing else, so it
cannot hand a handset to a person. Widening the read policy was the alternative
and is the wrong one.

**Why no test saw it.** `test_sync.py › a brand new device registers and pushes
in one flow` has covered this exact flow since phase 0 and kept passing. Every
route-level test installs an organisation-wide principal, so `dcp_org_wide()` is
true and the read policy never bites. The fixture rule again, one level up: it
was not the fixture's rows that fell inside the scope under test, it was the
fixture's *principal*. Breaks 210 and 211, and a new paragraph in the
conventions.

## An enumerator has no dashboard

Signed in to the console as `enumerator`:

> **Signed in as Dev Enumerator.** Your account holds no console permissions.
> Your work is on the handset: sign in there with the same username and
> password, and sync.

No navigation, and the deep link `/projects/01PROJDEV/monitoring` renders the
same page rather than the dashboard. The server refuses independently — all four
routes answer 403 with a reason a client can act on:

```
{"reason":"permission_denied",
 "message":"This needs submission.view, which this account does not hold."}
```

Both halves matter. The console hiding a screen is not a guarantee; the 403 is.

## A finding this run reported and then withdrew

The first version of this record ended with a defect: "paging forward in
Household Survey v1 does nothing, the indicator stays at `1 / 3`", read as
either the reachability guard missing an unanswerable form or the renderer
dropping questions. **It was neither. There is no defect, and the cause was
the run.**

The Next button sits in a bar pinned to the bottom of the screen. Its
coordinate was read off a screenshot scaled to 900x2000 from the device's
1080x2400 and converted from the wrong row, so every "tap Next" landed in the
blank space in the middle of the form. The app did nothing because nothing was
tapped. Walked again with the right coordinate, the form behaves exactly as
the spec says:

- `intro` is not a `field-list` group, so each of its three questions gets its
  own screen (§11.1). `1 / 3` is the first of three.
- Next moves to **2 / 3**, "Interview date", with a date picker.
- Next moves to **3 / 3**, "Does the respondent consent to the interview?",
  rendered with Yes and No, and the button becomes **Finalize** because that is
  the last currently reachable screen.
- Answering Yes turns the counter into **3 / 24** and Finalize back into Next,
  because the nine groups gated on consent have just become reachable.

So the counter never claimed a screen that could not be reached. It counts
*currently relevant* screens and recounts on every answer, which is why it read
3 while consent was unanswered — the honest number at that moment, and the
opposite of the failure it was suspected of.

The reachability guard has nothing to refuse here either: every question in
`intro` is ungated, and the form is collectable from the first screen.

**The lesson is about the method, not the code.** A control that "does nothing"
is two claims — the app ignored the tap, and the tap reached the app — and only
the first is about the software. The run inferred a defect from the app's
silence without establishing the second, and the seed form's being walked
past in every run since made the wrong conclusion sound more likely rather than
less. Confirm the input landed before reporting that the output is missing.
