# End-to-end run, 7 September 2026

The first time the builder ran in a browser against a real backend, and the
first time a form authored in it reached a handset. Everything below is what
was seen, not what a test asserts. Screenshots were taken at each step; the
observations are recorded here because a screenshot is not a record (rule 12).

**Setup.** Docker Desktop started; `docker compose up -d postgres redis
minio`. The existing `pgdata` volume held a half-migrated database from an
earlier session (`alembic upgrade head` refused on a duplicate column and the
seed refused a different `household_survey` v1), so a fresh `dcp_e2e` database
was created beside it rather than wiping the volume, migrated, seeded, and the
API run against it (`DATABASE_URL=...dcp_e2e`). Console on 5173 via `npm run
dev`. Emulator `Pixel_8`, app installed with `:clients:androidApp:installDebug`.

## The chain, and it ran end to end

1. `/forms` listed the seeded survey; a new form `clinic_intake` was created
   for the dev project and the builder opened on it, saved at revision 1, with
   the plan pane showing the server's "no questions" refusal verbatim.
2. From the palette: text, integer, select_one, date at the top level; a
   plain group holding a text; a field-list group holding a text and an image;
   a repeat holding a text and a decimal. Twenty-six autosaves by the end.
3. **The plan view agreed with the tree at every step**: seven screens, the
   repeat as one roster screen with two row screens, the field-list as one
   screen "with 1 others". After each edit the badges read stale and the plan
   pane kept the old numbers dimmed with its note until the next answer landed.
4. Choices for the select (inline, yes/no), required always. The label edit
   flowed straight into the plan pane.
5. Relevance on the field-list group built **visually** (`select_one = yes`);
   the Code tab then rendered it from the server as `${select_one} = 'yes'`.
   Relevance on the group's text typed in the **code field** (`${integer} > 0`).
   Relevance on the repeat's decimal typed in code with a deliberate half:
   `${text_4} =` drew the caret at the end with "the expression ends sooner
   than expected", then `${text_4} != 'skip'` saved.
6. **The reference picker showed what §2 says.** From the group, outside the
   repeat: every field, with `repeat[0].text_4 — first instance` and
   `repeat[].text_4 — every instance (inside count, sum, min, max only)`. From
   the decimal inside the repeat: "This instance — repeat" first with bare
   `text_4` and `decimal`, then "Form", then "Group › page".
7. **Round trip survived a real edit-save-reopen**: back to `/forms`, "Open
   draft", and both expressions came back — the visual one as its terms, the
   code one as the same text.
8. The repeat's source switched to a fixed list. **With the list still empty
   the gate refused at once**, in the plan pane, with step 2's sentence:
   `'repeat' never holds an instance: its fixed list is empty and rows cannot
   be added, so 2 question(s) inside it would never be asked: 'text_4',
   'decimal' (Form IR §10.3).` Two rows (mother, father) and a bind on `text_4`
   made it live again.
9. `false()` on the plain group: refused at edit time (`'group' is never
   shown: its relevant is statically false, so 3 question(s) inside it would
   never be asked: 'text_2', 'image', 'text_3'`), and **Publish refused with
   the same text**. Cleared, published as version 1, deployed to development.
10. **No console error or exception** at any point; no 5xx in the API log.
11. Handset: the fresh device self-registered on Sync, pulled the manifest,
    fetched the version, and "Which form?" offered **Clinic intake · v1**. Seven
    screens, the same seven. Text, integer 5, consent Yes, date; the field-list
    page appeared (consent was yes) with both questions on one screen; the last
    screen appeared (integer > 0). Finalize, Sync: `POST /sync/push` 200, and
    the server holds one finalized `clinic_intake` submission.

## What was seen that no test looked at

Console defects, all in step 6's panes.

> **All five were fixed the same day**, in `21c0467` ("fix: the five console
> defects the first end-to-end run showed"), and each was verified still fixed
> in the source on 13 September 2026. They are left here as the record of what
> the run found — a run record is evidence of what was seen, not a status board
> — but the status belongs beside them, because this list was read six days
> later as a list of open defects and a day of work was planned against it
> (`docs/is-the-builder-usable.md` §3.0, corrected).

- **Popovers do not dismiss.** The Insert-field picker stays open on Escape
  and on a click into the code textarea, and typing then lands in its filter
  box. The publish panel likewise ignores Escape.
- **The Add menu is clipped** by the tree pane's scroll container, so the
  registry notes on disabled types are cut mid-word ("In §2.1 as a media…").
- **Badges overlap labels.** In the stale state the badges sit over the node
  labels; the roster badge covers the repeat's label even when current; labels
  truncate to "inte…", "sel…" at the tree's 18rem.
- **The publish panel keeps a previous refusal** after the document changes,
  until the next attempt.
- **Accessibility**: palette menu items and the tree's select buttons have no
  accessible name; automation had to match on inner text.

Platform, seen through the chain:

- **The handset's roster screen is blank** (defect 20). Screen 5 of 7 showed
  nothing: no rows, no "Mother"/"Father", no way to enter an instance. The
  roster UI is the half of item 3 that was left, and this is what the gap looks
  like on a phone — the two questions inside cannot be answered, one level
  above the gate step 2 just closed.
- **A version deployed only to development never reaches a handset** (defect
  3): a device in a project with three environments is always on production.
  The console offered "development", reported success, and the form did not
  arrive until it was published again with production checked — "Already
  published as version 1. Deployed to production, development."
- **A stale cursor against a rebuilt database pulls nothing.** The device that
  had synced with the earlier database sent `cursor=287`; the fresh database
  had fewer entries, the pull returned 200 with nothing, and the app said "All
  changes synced". A test-environment artefact, but a rebuilt server would
  present exactly this. `pm clear` gave a fresh device.
- The emulator's settings still pointed at port 8001 from an earlier session;
  the app's own message named the port and the fix.
