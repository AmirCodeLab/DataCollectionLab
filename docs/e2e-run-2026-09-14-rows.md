# End-to-end run: MICS6 HL14 authored in the builder and answered on a phone

**Date:** 14 September 2026
**What was run:** Form IR §3.3's `rows` choice list — the feature
`docs/proposal-row-choice-question.md` proposed and
`docs/decision-rows-self-exclusion.md` finished — from an empty form in the
console to an answer on an Android runtime.
**Stack:** uvicorn on :8010 against a scratch PostGIS (the project's own
Postgres port was taken), `npm run dev` proxying to it, the Wasm engine
rebuilt from this branch, `Pixel_8` emulator, debug build installed.

---

## 0. What it proves, and the two things it found

**It works.** A programme manager can author HL14 in the builder, publish it,
and an enumerator can answer it on a phone: every member's row offers the other
members and not the person on it, deleting somebody else leaves the answer
naming the same person, and deleting the referent is a visible error that stops
finalisation.

**It found two things that no suite could**, which is what a real run is for:

1. **The console's preview was resolving the wrong row's list** — after both
   engines, both vector suites and the handset's view model were already right.
   Break 242, §2.
2. **The Android app died on opening any form**, and had done since PR #64 —
   a §7.1 regex that every test engine accepts and the phone's does not.
   Defect 33, §3.

---

## 1. The builder, as `pm`

A new form, `mics6_hl_rows`, built with no terminal and no API call: a repeat
`members` with `hl2_name` and `hl14_mother_line`, the second a `select_one`
whose choices are `{"kind": "rows", "repeat": "members", "excludeSelf": true}`.

What the screens did, in the order they did it:

- **`rows` is offered in the source list**, from the palette — the registry
  over the wire, so listing it in `collectable-types-v0.1.json` is what made it
  appear.
- **Picking it defaulted "rows of" to `members`**, the repeat the question is
  in, rather than to nothing. That is the case the feature exists for and it is
  also the only placement where the next control is legal.
- **The warning appeared twice, in two voices, and both were right.** The
  properties pane said *"members has no summary label, so this question will
  offer position numbers — 1, 2, 3 — rather than names (§10.3). Set one on the
  repeat."* The screen-plan pane said the **server's** §10.3 warning, verbatim:
  *"hl14_mother_line: chooses from the rows of repeat 'members', which has no
  summaryLabel, so the options are position numbers"*. Setting
  `summaryLabel` to `{0}` over `${hl2_name}` cleared both.
- **"Not the person on this row" was offered** with the MICS6 sentence under
  it, because the question is inside `members`.
- **Publish accepted it** — version 1, deployed to production and development —
  which is `check_collectability` agreeing that a client can present a `rows`
  list.

## 2. The preview, and break 242

Three members: Zubaida, Bilal, Amina. On Amina's row the preview offered
**Bilal and Amina**.

That is her own name offered as her own mother, and Zubaida missing — and it
looks entirely plausible: three real names, two options, a list. Unless you know
the roster you would read it as correct.

`PreviewSession.questionJson` asked the engine for `choices(fieldId)`. A rows
list is a function of (field, instance), so by field id every row of the roster
gets the **first** row's list. The same defect `CollectionViewModel` had, in the
third place the decision is made, and the last one left.

Everything below it was already right: `repeat-016` and `repeat-017` green on
three targets, `RowChoiceScopeTest` green, breaks 237–241 watched and reverted.
**The engine can only answer the question it is asked**, and no vector can see
who is asking. Break 242; `PreviewSessionTest` now walks this fixture.

After the fix, on the same three members:

| Row | Offered |
|---|---|
| Zubaida | Bilal, Amina |
| Amina | Zubaida, Bilal |

Then, on Zubaida's row with Bilal chosen: deleting **Amina** left the answer
alone and the footer still read "This form would finalize"; deleting **Bilal**
turned it into *"Cannot finalize: 1 answer(s) need attention"*. Both halves of
§3.3's membership rule, in a browser.

## 3. The handset, and defect 33

The device synced (2 forms deployed, downloaded through the Updates screen),
the form list offered `MICS6 HL — list of household members · v1`, and tapping
it **closed the app**.

```
FATAL EXCEPTION: main
java.lang.ExceptionInInitializerError
    at com.dcp.form.CompiledForm.warnUnfilledSlots(Runtime.kt:416)
    at com.dcp.form.CompiledForm.checkInterpolation(Runtime.kt:444)
Caused by: java.util.regex.PatternSyntaxException: Syntax error in regexp pattern near index 6
\{\{|}}|\{(\d+)}
      ^
    at com.dcp.form.Interpolation.<clinit>(Text.kt:40)
```

**Nothing to do with this feature.** §7.1's slot pattern has carried a bare `}}`
since interpolation landed. `java.util.regex` accepts it; Android's
`com.android.icu` does not — and because the pattern is a `val` on an object,
the refusal arrives as `ExceptionInInitializerError` from the class
initialiser, so **any** form kills the app the moment it is compiled.

Why now, and why nothing caught it:

- PR #64's §10.3 unfilled-slot warning made `slotIndices` reachable for **every
  node of every form**, not only for nodes that have arguments. Before that, a
  form whose questions had no `labelArgs` never touched the pattern. The last
  handset run predates it.
- `jvmTest` and `testAndroidHostTest` both run on the **JVM's** regex engine —
  "androidHost" is the host, which is the point of it — and `wasmJsNodeTest`
  runs on JavaScript's. The one engine that rejects this is the one on a phone.

Fixed by escaping every brace (`\{\{|\}\}|\{(\d+)\}`, identical in meaning to
both engines). `InterpolationRegexTest` is the guard and is deliberately a
**source check**: a test that compiled the pattern would pass here for exactly
the reason the bug shipped.

## 4. The handset, answering HL14

Three members again — Zubaida, Bilal, Amina — added on the device.

| Row | HL14 offered |
|---|---|
| Amina (row 3 of 3) | Zubaida, Bilal |
| Zubaida (row 1 of 3) | Bilal, Amina |

Amina's mother recorded as Zubaida. Then:

- **Deleted Bilal** — somebody else. Amina's row still read *Zubaida*, selected,
  with no error. The answer means the same person; it is not a position that
  slid.
- **Deleted Zubaida** — the referent. Amina's HL14 turned red: **"Invalid
  answer"**, and `Finalize` refused with *"Cannot finalize: 1 answer(s) need
  attention"*, sending the enumerator to that screen.

That is §6.3 and §6.2 doing on a phone what `repeat-016` and `repeat-017` assert
in the abstract, and it is the behaviour the positional design could not have:
there, deleting Bilal would have silently repointed Amina's mother at somebody
else and nothing would have gone red at all.

**One thing worth improving, filed as defect 34.** "Invalid answer" is the
client's generic sentence for any non-`required` error. For a rows question the
true sentence is *the person this refers to is no longer on the list*, which is
what the enumerator needs to know to re-answer. The engine reports the error
kind (`choice`); the client does not use it.

## 5. What this run did not cover

- **Sync of the answer.** The submission was left as a draft: what the id looks
  like in an export is `docs/phase2-record.md`'s ground and is unchanged by this
  feature — the value is a `select_one` answer like any other.
- **A second language.** The form was built in English only. §7.1's isolates are
  asserted by vectors and by `InterpolatedLabelTest`; nothing here adds to that.
- **A label that interpolates a name inside a row.** Still falls back to the raw
  label on both the handset and the preview, because the engine's *label*
  renderer scopes to the first instance — the §7.1 twin of the defect §2 fixed
  for choice lists. Untouched here, and now the only caller of that shape left.
