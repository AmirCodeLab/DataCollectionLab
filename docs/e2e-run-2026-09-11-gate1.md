# Gate 1 run, 11 September 2026 — an organisation no seed made

The first time this platform has been stood up rather than seeded. Everything
below is what was seen.

## Why this run is different from the five before it

Every previous end-to-end walk — items 0, 2, 4, 5 and 6 — ran against
`scripts/seed_dev.py`'s single organisation, `dev`, with its published
password. That is what "there is no way to create an organisation" meant in
practice: the product had never been used by anybody it was not seeded for.

This run is on `rcons`, created by `scripts/provision.py` against an empty
database, with an administrator whose password was typed.

## The guards, run rather than asserted

The point of A10 is that the operator action cannot be wrapped in a
convenience script. Three attempts:

**Piped stdin** — the shape a wrapper, a CI step and `ssh host 'provision …'`
all have:

```
Refused. This is not a terminal.
The administrator's password is typed, never passed — there is no flag and no
environment variable for it. That is deliberate: it is what stops this being
wrapped in a convenience script and pointed at production by accident.
```

Exit code 2.

**A slug that does not match the deployment**, checked before anything else
happens:

```
Refused. --slug is 'rcons' and ORGANIZATION_SLUG is 'dev'.
This deployment resolves one organisation, from that setting. An organisation
provisioned under any other slug exists, holds a working administrator, and
cannot be reached by the login.
```

**A second run against a database that already has the organisation** — the
production-accident case:

```
Refused. An organisation with the slug 'rcons' already exists
(01M28DBNWPJX8ZF8M26ZWZAQ7X). This script only creates; it will not touch it.
```

Nothing was changed. That is the property that matters: pointed at a live
database, the worst this tool can do is print a message.

Driven through a pty, because that is the only way it runs — which took a

## Then the console, as that administrator

Signed in as `fatima`. The projects screen offered **New project**, which no
console has ever had.

Created "Sindh household listing", slug `sindh-listing`, `standard`. The form
states the two things that cannot be undone — the slug is what URLs are built
from, the security mode is fixed — and says that all three environments come
with it. Afterwards:

| | |
|---|---|
| project | Sindh household listing / sindh-listing / standard |
| environments | development, production, staging |
| recipient keys | *not used in this mode* |

An administrator created a project on an organisation nothing seeded, and the
row links straight to its sample and its monitoring.

## What the run found

**The empty projects screen told a customer to run the dev seed.** Before any
project existed it read *"No projects. Run `scripts/seed_dev.py`."* — advice
that was **true until this gate**, because the seed was the only way a project
could come into being. A customer following it would run a script that refuses
outside development and publishes a password.

Nothing failed and nothing could have: no test asserts an empty state's
wording, and the sentence was correct when it was written. It is now "No
projects yet." Break 225, and the class is worth naming — *advice that was
correct becomes wrong the moment the thing it describes stops being the only
way, and nothing fails when it does.* It was found only because this run was
done on a provisioned organisation instead of the seeded one.

**And a browser cannot easily move between deployments.** Signing in to the
new organisation from a browser that had used the seeded one failed with
`invalid_credentials`, because `dcp_org` is `HttpOnly` on `/api` and the page
cannot clear it; the API kept resolving `dev`, which does not exist in the new
database. `POST /auth/logout` needs a valid session and so cannot help. The
run moved to a different host to get a clean cookie jar.

Not a defect in any deployment — one browser meets one deployment — but worth
knowing for anybody testing two, and it is exactly the kind of thing that only
appears when a second organisation exists for the first time.

## What this run did not cover

- **The keypair.** This project is `standard`, so it has no recipient keys and
  the screen says so. The generate-and-download path is unchanged by gate 1 and
  was walked in Phase 2; what gate 1 supplied was a project to generate one
  *for*. A run of an encrypting project belongs with the custody checklist in
  `docs/key-custody.md` §7, which needs two people.
- **A handset.** No device has synced against `rcons`. Gate 2 is where a real
  form arrives, and that is when it will.
- **A second organisation on one deployment.** `ORGANIZATION_SLUG` resolves
  one. The schema carries `organization_id` everywhere and nothing here
  exercised more than one.
