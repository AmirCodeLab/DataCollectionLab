# Item 4 run, 10 September 2026 — three actions, and what each costs before it is tapped

Against uvicorn on the dev database (migrations through 014) and the `Pixel_8`
emulator. The console half of item 4 is deliberately nothing new, so the
browser appears here only as the cause: a form version published and deployed
against a newer list. Everything below is what was seen.

## The setup, and what it is honest about

`village_check` is a two-question form — a required name and a
`select_one_from_file` on `villages` — published in English and Arabic so the
language toggle exists. Published through the API rather than through the
builder: the builder's publish path is item 0's surface and walking it adds
nothing item 4 is about. The console was opened to confirm what a PM sees,
which is the Forms page listing `village_check` with published versions 1, 2.
No console screen was added in this item.

- `villages` v1: 3 rows. `village_check` v1 pinned to it, deployed.
- `villages` v2: 4 rows. `village_check` v2 pinned to it, deployed.

## What the handset did

**A fresh install, never synced.** "Nothing has been synced to this device yet.
Tap Sync work to find out what this project has deployed to you." The first
version of that screen said "no form has been deployed to this device yet",
which the device could not know, and that is the first thing this run found.

**Sync work.** One request: `scope=forms,datasets,assignments`, `limit=200`.
It brought four of the enumerator's own submissions, both manifests, and **no
document and no row** — the server log shows zero `/forms/versions/` calls.
The line under the button reads "Updates waiting: 2 forms and 1 list", with no
size, because nothing of `villages` is held and there is no honest estimate to
make.

**Updates.** Two sections, each with its own status, both "Not checked yet".
Forms: two versions waiting, "A form is tens of kilobytes." Reference data:
"villages v1 — not downloaded" over "Full download — 3 rows." and a Download
button. Above both: "Your interviews are sent from the Submissions screen and
never wait for anything here."

**Update forms.** On the wire: `GET /sync/pull?cursor=13&limit=0&scope=forms,datasets`
— the manifest-only pull, no ops, cursor echoed — then the two documents. The
outcome, immediately: "2 forms downloaded. They need villages v1 — not
downloaded. Interviews can be started now; they cannot be finalised until it
arrives."

**The refusal.** Starting a Village check, the top of the form says "Reference
data has not arrived yet: villages. Open Updates to download it." The village
question renders with no options, which is the store refusing to serve an
unpinned list. Finalize:

> Cannot finalise: villages v1 not downloaded — tap Reference data.

**In Arabic.** The toggle switches the form to RTL. Two failures, both fixed
and both re-verified: the refusal stayed in English, and its full stop sat at
the far left of the line. After the fix the sentence is Arabic, built from the
same facts, with `villages v1` isolated as an LTR run inside it.

**Download, then finalise.** Reference data → Download → "villages: 3 rows."
Both sections settle with their own timestamps. Reopening the draft, the
village list offers Amwe, Bwana, Chumvi, the notice is gone, and Finalize
succeeds.

**The scenario as asked: a newer list.** With `villages` v2 and `village_check`
v2 published, **sync work only**:

- "Updates waiting: 1 form and 1 list"; still no document fetched.
- Updates → Update forms → "1 form downloaded. They need villages v2 — not
  downloaded…"
- Starting a v2 interview and finalising: "Cannot finalise: villages v2 not
  downloaded — tap Reference data."
- The list card now reads "villages v2 — not downloaded" over "Update from v1
  — only the rows that changed. The whole list is about 116 bytes.", and the
  button says **Update**, not Download.
- Tapping it: `GET /datasets/versions/{v1}/delta?...` and **one row**
  transferred, not four. "villages: 1 row."
- Reopening the draft and finalising: **Village check v2 — Finalized.**

## What the run found that no test was looking at

1. **A device speaking for a server it had never reached** (break 200).
2. **A notice that never reached the screen**: emitted as a sibling of the
   question list in the Scaffold's content slot, where children stack, so the
   list drew over it. Written long before item 4, never seen (break 201).
3. **The screen contradicting the gate**: readiness read once at load, so after
   a download the notice still said the list was missing while the gate would
   have allowed the interview. Known defect 24's shape with the screen as the
   stale one (break 202).
4. **A refusal frozen in one language**, and the bidi failure beside it
   (break 203).
5. **"about 0 KB"** on the button that spends a connection, and a button
   reading "Download" over a line reading "Update from v1" (break 204).

The badge on the submissions screen also did not refresh on returning from
Updates; it follows the form and dataset tables now.

## Not shown by this run

- A list large enough for the delta to matter in seconds rather than bytes.
  The measured figures for that are break 52's, on 38,000 rows.
- A partially transferred list resuming, which `SeparateSyncTest` covers with
  a cursor but no phone did here.
- Media, which rides the work sync unchanged.
